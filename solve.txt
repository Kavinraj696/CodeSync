PHASE 1 — AUTHENTICATION AND SECURITY
==================================================

Harden authentication throughout the entire application.

1. JWT SECRET

Current implementation has a fallback JWT secret.

Remove insecure production fallback.

Production behavior:

if JWT_SECRET is missing:
    fail startup

Development may optionally use a clearly marked development-only secret.

Never expose JWT_SECRET to frontend code.

2. HTTP AUTHENTICATION

Ensure all protected APIs use JWT authentication.

Public endpoints should be explicitly defined.

Protected endpoints must reject:
- missing token
- invalid token
- expired token

Use correct HTTP statuses.

3. SOCKET.IO AUTHENTICATION

This is critical.

Currently Socket.IO clients can connect and provide userId/roomId themselves.

Implement JWT authentication during the Socket.IO handshake.

Client should send:

auth: {
    token
}

Server should verify the JWT before allowing connection.

Attach authenticated user to:

socket.user

Never trust userId supplied by the client.

4. WORKSPACE AUTHORIZATION

Create centralized authorization helpers.

Example:

requireWorkspaceMember(roomId)
requireWorkspaceRole(roomId, role)
canReadWorkspace()
canEditWorkspace()
canUseTerminal()
canUseGit()
canManageMembers()

Roles:

owner
editor
viewer

Permissions:

OWNER:
- everything

EDITOR:
- read files
- edit files
- create/delete files
- terminal
- run code
- Git operations according to project policy
- AI

VIEWER:
- read files
- see collaboration
- cannot modify files
- cannot use terminal
- cannot execute code
- cannot commit/push
- cannot delete files

Never rely on frontend role checks for security.

Frontend checks are only UX.

Backend must enforce permissions.

5. SOCKET AUTHORIZATION

For every socket event verify:

- authenticated user
- workspace membership
- permission for requested action

Do not trust:
- roomId
- userId
- role
- terminalId
- filepath

from client without verification.

PHASE 2 — COLLABORATIVE EDITING
==================================================

This is the highest priority feature.

The current system broadcasts entire file contents through Socket.IO.

This is not sufficient for concurrent editing.

Implement proper collaborative editing.

Preferred architecture:

Yjs + y-websocket-compatible synchronization or an equivalent CRDT solution.

If using Socket.IO instead of a separate websocket server, implement a proper Yjs transport over the existing Socket.IO infrastructure.

DO NOT create a simplistic "last update wins" system.

Requirements:

1. Multiple users can edit the same file simultaneously.

Example:

User A edits line 10.
User B edits line 20.

Both changes must survive.

2. Concurrent insertions must merge correctly.

3. Concurrent deletions must not corrupt document state.

4. Local changes should appear immediately.

5. Remote changes should appear immediately.

6. No full-document replacement for every keystroke.

7. Support reconnect.

8. Support offline local edits.

9. Reconcile changes after reconnect.

10. Persist document state safely.

Use:
- CRDT document
- update vectors/state
- persistence
- synchronization protocol

Do not store only the latest file content as the collaboration state.
